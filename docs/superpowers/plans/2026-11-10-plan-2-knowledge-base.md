# Educational Agent — Plan 2: Knowledge Base and Ingestion (Implementation Plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The student adds each week's material (files, pasted transcripts, web links, books) in a Library page; a resumable background worker parses, chunks, embeds and stores it with exact locations; the student reviews suggested topics per file; and the Tutor searches the material through a knowledge-base MCP server with hybrid search, naming the slide or page it used.

**Architecture:** A new `eduagent.kb` package holds plain-code ingestion (parsers → blocks → chunker → embedder → stores) and retrieval (dense in Chroma + keyword in SQLite FTS5, fused and reranked). Ingestion runs **inside the app process on one background thread** (design §3.9), one file at a time in strict queue order, checkpointed per 25-page piece in SQLite. Retrieval runs **inside the KB MCP server**, a stdio child process started by ADK's `McpToolset`; it reads the same `study.db` (WAL) and the same Chroma server (`chroma run`, started by the launcher). SQLite is the source of truth for chunk text, locations and topic links; Chroma holds only vectors plus filter metadata.

**Tech Stack:** Plan 1 stack plus: chromadb 1.5.x (`chroma run` Rust server + `HttpClient`) · docling 2.149 (PDF/PPTX/DOCX; RapidOCR for picture regions; CodeFormula) · pypdfium2, python-pptx, python-docx (cheap peeks) · fastembed (MiniLM-L6 cross-encoder, ONNX) · trafilatura 2.3 + httpx (web links) · `google-adk[mcp]` (mcp 2.3, `MCPServer`, formerly FastMCP) · SQLite FTS5 · dev: reportlab (test PDFs).

**Spec:** `docs/superpowers/specs/2026-11-10-plan-2-knowledge-base-design.md` (binding for Plan 2), then `docs/superpowers/specs/2026-11-05-educational-agent-design.md` (binding wherever the Plan 2 design is silent). Implementers read both. Where this plan says "design §X" it means the Plan 2 design.

**Process (student's rules, design §9):** branch `plan-2-knowledge-base`; superpowers:subagent-driven-development with implementer → task review → fix rounds → scoped re-review for every task; every finding, minor and ruling in the ledger. After each task passes review the controller pushes the branch (never `main`), then stops and teaches (what / why / why this way and not another / what reviews caught) and waits for "continue". No Co-Authored-By or AI attribution in commits or PRs. Never delete local branches; ask before deleting the ledger.

## Global Constraints

- Everything from Plan 1's Global Constraints still holds (Python 3.12 + uv, src layout, pure Python UI, `127.0.0.1` only, `log = logging.getLogger(__name__)` and the level rules, course text only at `DEBUG`, API keys never in traces/logs/UI, `WHAT_IT_DOES` on every component module and listed in `tests/test_what_it_does.py`, "Decisions to record" appended to `docs/decisions.md` after each task).
- `data/`, `.env`, `.venv/`, `.superpowers/` stay git-ignored. **Nothing from the student's course is ever committed.** Test fixtures are generated by the tests themselves (python-pptx, python-docx, reportlab, Pillow) with text written for the tests.
- All downloaded models (Docling layout/table/CodeFormula, RapidOCR, reranker) live under `MODELS_DIR` (default `data/models`, on Y:). Nothing is downloaded to `C:\Users\...\.cache`.
- Chroma: only the Rust server via `chroma run --path <data>/chroma --host 127.0.0.1 --port <CHROMA_PORT>`; never `chromadb.PersistentClient` or the Python FastAPI server (CVE-2026-45829). Every component uses `chromadb.HttpClient(host="127.0.0.1", port=CHROMA_PORT)`.
- Ollama at `http://127.0.0.1:11434`. **Before any `ollama`-marked test or live check, confirm `GET /api/tags` lists `qwen3:4b-instruct` and `nomic-embed-text`; if Ollama is unreachable, start `ollama serve` in the background first.**
- Embedding prefixes are exact: documents `search_document: `, queries `search_query: `; topic-name similarity uses `clustering: `. Every `/api/embed` call sends `"truncate": false`.
- Stdout is reserved for MCP stdio. The KB MCP server logs only to stderr and its own file `data/logs/kb-mcp.log`.
- Test markers: `ollama` (needs Ollama), `models` (downloads or runs Docling PDF models or the reranker). Default run: `-m 'not ollama and not models'`. Every task whose unit tests use fakes for a model also runs its live check (marked tests) and reports the output.
- Exact user-facing copy fixed by the design (quoted verbatim where it appears below) must not be reworded.
- Commit after every task with a conventional message and **no AI attribution lines**.

## Review Focus

1. **A file the parsers choke on** (corrupt or 0-byte PDF, password-protected PDF, PPTX with no slides, a `.pdf` that is really HTML). Expected: that file shows _failed_ with a plain-English reason, the next file in the queue still runs, the app never crashes. → `test_bad_file_fails_and_queue_continues` (Task 15), `test_encrypted_pdf_plain_reason` and `test_not_really_a_pdf` (Task 11).
2. **The app is closed in the middle of a book.** Expected: on the next start the book resumes at the first unfinished 25-page piece, and no chunk is duplicated in SQLite, FTS or Chroma. → `test_resume_skips_done_pieces_without_duplicates` (Task 15).
3. **A chunk too long for the embedding model** (a code listing or wide table, whose characters cost far more tokens than prose). Expected: the chunker splits it before embedding; Ollama never returns HTTP 400 and the file still finishes. → `test_embedding_text_never_exceeds_cap` (Task 10), `test_overlong_input_raises_clear_error` (Task 8).
4. **Searching after a file was deleted or replaced.** Expected: none of its chunks come back from dense or keyword search or `get_topic_chunks`, and their ids are listed in `removed_chunks`. → `test_deleted_file_never_searchable` (Task 16), `test_replace_removes_old_only_after_new_finishes` (Task 16).
5. **Awkward file names** (spaces, Unicode, `CON.pptx`, 200-character names, the same name in two modules). Expected: each file is stored safely and separately and its original name shows in the Library. → `test_stored_path_is_safe_and_unique` (Task 16).

Slots a group can't fill with relevant chunks go to the other group; each group then fills its final slots from its ranked list. Merged list sorted by score.                                                                                                | Satisfies "a question only the book covers returns up to 10 book chunks" while never returning fewer chunks than exist: the floor only moves slots, it never empties results. With the reranker off, only empty groups give slots away.                                                                      |

| Topic tagging            | Qwen reads module files in windows of ≤ 1,500 words, chunks numbered `[1]…[n]` (each cut to 300 words), and returns JSON `[{"topic": str, "chunks": [int]}]`, 2–6 topics per window, using existing course topic names verbatim when they fit. Tagging failure must not hide searchable material.                                                                                             |

Thresholds are constants with a recorded calibration.                                                                                                                                              |
| Module suggestion        | Peek at the first ~300 words (title slide, first page, first paragraphs, paste title). A regex for `(module                                                                                                                                                                                                                                                                                                                                  | week                                                                                                                                                                                                                                                                                                         | unit | lecture | chapter | topic)\s\*\d+`matches an existing module by number, otherwise Qwen picks an existing module or proposes`Module N: <title>` (temperature 0). A portrait PDF of ≥ 80 pages is suggested as **Course reference (book)**. Ollama down → no suggestion, the picker starts empty. | The regex handles most title slides instantly; Qwen only for the rest. The book heuristic matches the student's "PDFs are mostly books". |
| Tutor tool wiring        | `McpToolset` over stdio (`sys.executable -m eduagent.kb.mcp_server`, `cwd` = app cwd), `tool_filter=["search_material"]`. A `before_tool_callback` overwrites `course_id` (from the thread) and `limit`; an `after_tool_callback` returns the tool's `structuredContent` (or the parsed text block) so the model sees one clean dict, not the same JSON twice.                                                                               | The model can't pick the wrong course; ADK passes the whole MCP `CallToolResult` (text block + `structuredContent`) to the model, which would double the tokens.                                                                                                                                             |
| Retrieval trace          | The tool result is `{"chunks": [...], "trace": {...}}`; the compact trace (~300 tokens) stays in what the model sees, and ChatService's existing `tool_result` step stores it.                                                                                                                                                                                                                                                               | Meets the roadmap ("saved into the `tool_result` step") with no second recording path. Hiding it from the model would need the callback to write trace steps itself and risk duplicates.                                                                                                                     |
| Qwen context             | All Qwen calls (classifier, tutor, tagging, module suggestion) send the same `num_ctx = QWEN_NUM_CTX` (default 8192); Qwen gets `SEARCH_RESULTS_QWEN` (default 6: 4 module + 2 book) instead of 10. Both are measured in Tasks 4 and 19.                                                                                                                                                                                                     | Ollama's default context on a CPU-only machine is 4096 and it **silently drops the start of longer prompts**; 10 chunks ≈ 6,500 tokens. A different `num_ctx` per call makes Ollama reload the model every time. 8192 costs ~1.2 GB of KV cache (36 layers × 8 KV heads × 128 × 2 × 2 bytes ≈ 147 KB/token). |
| Qwen timeout             | `QWEN_TIMEOUT_S` (default 240): `asyncio.wait_for` around the classifier call and around every Qwen call in `RoutedLlm` (direct and fallback); a timeout in the classifier → default route; in the reply → the existing "Something went wrong" reply.                                                                                                                                                                                        | One setting, as the carry-forward asks. 240 s leaves headroom for a cold load (~15 s) plus a ~5k-token prompt on CPU; Task 4 measures it.                                                                                                                                                                    |
| Week label               | `courses.week1_monday` = the Monday of the week of the course's first upload, set once. `uploaded_week = (upload_monday − week1_monday).days // 7 + 1`.                                                                                                                                                                                                                                                                                      | Stable: deleting the first file doesn't renumber every later week.                                                                                                                                                                                                                                           |
| Replace                  | The new version is queued with `replaces_file_id`; the old file is purged **after the new one finishes**. If the new one fails, the old stays and the reason says "the previous version is still in use".                                                                                                                                                                                                                                    | Material never disappears from search during a long re-ingest or after a failed one.                                                                                                                                                                                                                         |

| Retry                    | A failed file goes back to the **end** of the queue.                                                                                                                                                                                                                                                                                                                                                                                         | Strict FIFO: a retry is a new request.                                                                                                                                                                                                                                                                       |
| Duplicate web content    | A URL already in the course → the Replace dialog at add time. After the fetch, a snapshot whose hash matches an existing file → status `skipped` with "Same content as <title> — skipped".                                                                                                                                                                                                                                                   | The content of a link is only known after downloading it.                                                                                                                                                                                                                                                    |
| Upload limit             | `MAX_UPLOAD_MB = 300` (constant), web downloads capped at 20 MB, 20 s timeout.                                                                                                                                                                                                                                                                                                                                                               | Books can be large; a cap stops a mistaken multi-GB drop. Not a setting (YAGNI).                                                                                                                                                                                                                             |

**Files:** Modify `config.py`, `.env.example`, `models/qwen.py`, `models/routed_llm.py`, `team/routing.py`; tests in `tests/models/test_qwen.py`, `tests/models/test_routed_llm.py`, `tests/team/test_routing.py`, `tests/test_config.py`.
